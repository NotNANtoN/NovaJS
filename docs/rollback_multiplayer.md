# Rollback Multiplayer Plan

This document is the plan for adding rollback netcode (deterministic lockstep with rewind/resimulate) to NovaJS. It replaces the earlier notes version of this file and builds on the completed work in [docs/engine_in_webworker.md](./engine_in_webworker.md).

## The Model

- Every peer in a star system runs the full simulation for that system.
- The only thing exchanged over the network is per-tick player input, plus occasional snapshots for joins and desync recovery.
- Each peer predicts remote inputs (repeat-last-input), and when real inputs arrive for a past tick, it rolls back to a stored snapshot, applies the true inputs, and resimulates to the present.
- The server stops being a simulation authority within a system and becomes an input relay, tick clock, and snapshot archive for late joiners. Because the sim is deterministic, the server *can* still run any room's simulation like any other peer (for NPC authority, validation, or persistence) — but steady-state NPC behavior is computed identically by every peer and needs no owner. (Today all NPCs are simulated by clients.)
- The existing room-per-system infrastructure (`multi_room_communicator.ts`) is reused as-is: rollback state is scoped to one star system's world, which keeps entity counts and snapshot sizes bounded.

## Why the plan has this shape

The original three steps (worker split, determinism, state history) are the right skeleton, but two of them hide most of the work, and the ordering within them matters:

1. **Step 1 (worker split) is structurally done** on the `worker` branch (lingering issues in Phase 0 below) and its shape is right for rollback: input already crosses the bridge as normalized `ControlEvent`s/commands, the sim world is free of PIXI/browser state, and display consumes snapshots. Nothing about the current bridge design blocks rollback.
2. **Step 2 (determinism) is the long pole**, and it is much more than fixed timestep + seeded RNG. The audit below found six categories of nondeterminism, of which async data loading inside the simulation is the most invasive to fix.
3. **Step 3 (state history) should be built and validated entirely locally** — rollback correctness can be tested with zero networking by feeding the sim its own inputs with artificial delay. The network protocol is the *last* thing to build, not part of step 3.
4. A step the original plan was missing: **a determinism verification harness must come first**, not last. Without per-tick state hashing and record/replay tests, desyncs are undebuggable. Every subsequent change gets validated against this harness.

## Determinism audit findings

What must change in the current code, by category:

| Category | Sites | Notes |
|---|---|---|
| Variable timestep | `time_plugin.ts:20-27` | `delta_ms` from wall clock each frame; foundation fix |
| Wall-clock time in gameplay | `stat.ts:160`, `npc_plugin.ts:32` (via `time.time`), `projectile_plugin.ts:196` (fire time) | must become tick-derived logical time |
| `Math.random()` in sim | `fire_weapon_plugin.ts:101,130`, `make_ship.ts:17-19`, `ship_plugin.ts:166-168`, `npc_plugin.ts:45` | ~6 sites; replace with a seeded PRNG resource. Display-world uses of `Math.random` (explosions, beams, animation jitter) are fine and stay. |
| Random entity UUIDs | `projectile_plugin.ts:177,378`, `bay_plugin.ts:118`, `beam_plugin.ts:109` | `v4()` per spawn; replace with deterministic IDs (e.g. `${spawnTick}:${counter}`); counter becomes snapshotted state |
| Async in the sim step path | `ProvideAsync`/`AsyncSystem` uses: `ship_plugin.ts`, `outfit_plugin.ts`, `planet_plugin.ts`, `projectile_plugin.ts:245`, `collisions_plugin.ts:140` (hulls), `fire_weapon_plugin.ts:361` (weapon data), `make_system.ts:22` | **The most invasive item.** Components appear on entities at a tick that depends on cache warmth. All static game data must be resolved *before* an entity enters the sim world (preload at system creation / spawn time), making these providers synchronous. |
| Cross-engine float math | trig throughout movement/weapons | IEEE 754 `+ - * / sqrt` are deterministic everywhere; `Math.sin/cos/atan2/pow` are **not guaranteed identical across JS engines**. Decision: assume latest Chrome for all clients, and periodically broadcast full position/velocity/rotation for ships as a drift backstop. Projectiles are short-lived enough not to matter. |

Things that are already in good shape:

- System execution order is topologically sorted and stable given stable plugin registration order (`world.ts:266`).
- Entity iteration is Map insertion order — deterministic, **but snapshot restore must rebuild the entity map in the recorded order**, or post-rollback iteration diverges from the original timeline.
- The event queue is synchronous FIFO within a step.
- Input already flows as per-tick `ControlStateEvent`s and bridge commands rather than direct mutation.
- `randomAdmin()` in `multiplayer_plugin.ts:173` is network-layer, not sim state; it doesn't need fixing for determinism.

## Phases

### Phase 0: Land the worker branch

Do not abandon `worker` (branched off `turborepo`). The sim/display split's shape is exactly what rollback needs. Finish and commit the in-flight work; rollback work happens on a new branch on top of it.

Known lingering issues to resolve or explicitly defer:

1. ~~Desync when a ship dies~~ **Fixed.** Root cause: every peer (including the server's replica worlds, which run their own weapons fire with unseeded RNG) decided deaths independently and deleted entities locally, racing the owner's deltas — dead ships could resurrect via state requests or persist as zombies on peers that missed the removal. Entity removal now has a single authority (the owner's sim; death VFX still run everywhere), and state-request responses report unknown entities as removed. Additionally, `MovementState` deltas were only sent on input changes, so the respawn teleport after a player death never reached other players — discontinuous moves now bump a `teleportCount` field that forces a full movement state send (`teleport()` in the movement plugin; use it for any future respawn/blink mechanics instead of writing `position` directly). This is a patch over the divergent-simulation model, not a cure — the cure is rollback itself. Still open from that investigation: one unreproduced total sim freeze (worker wedged silently, no errors — observed once, before these fixes, with a point-defense-equipped player ship), rapid spawn/despawn cycling of unnamed bay fighters, and a stray `window is not defined` rejection from the worker bundle.
2. ~~Per-frame sync performance~~ **Investigated and largely fixed.** Benchmarking (`snapshot_benchmark.ts`) plus a Chrome trace showed the worker was ~82% idle and the cost was on the main thread: full-frame apply re-setting every component of every entity each frame, which fanned out through the ECS query-cache invalidation, plus Immer overhead in the multiplayer DeltaMaker. The bridge now sends delta frames (host string-compares each component's encoded form against the last frame — no Immer), cutting frame size ~5x and main-thread clone+decode ~3x. Remaining known main-thread costs, deferred: PIXI `removeChild`/`removeItems` churn from transient entities and particle emitter update/upload (display-layer, unrelated to sync), and ECS query-cache invalidation cost in general (matters again for rollback resimulation; see Phase 1).

### Phase 1: Determinism foundation (single-player, no networking)

1. ~~**Determinism harness first.**~~ **Done.** `hashWorld`/`diffWorldHashes` (nova_ecs `world_hash.ts`) hash all serializer-registered entity state in canonical order; `determinism_harness.ts` steps two identical worlds in lockstep and reports the first divergent tick and entities. `determinism_test.ts` is the CI gate: a quiet world is bit-identical over 240 steps. `determinism_check.js [npcs] [steps]` is the diagnostic — with NPCs it correctly reports divergence (Math.random + v4 uuids, items 4–5). Pause/single-step ship as `window.novaSim.pause()/.resume()/.step(n)`.
2. ~~**Fixed timestep.**~~ **Done, 60 Hz.** `FixedTimestepResource` + `useFixedTimestep(world, delta_ms)` in the time plugin; `makeSystem` puts every simulation world on fixed, 0-based time. The client pump and the server stepper own accumulators (bounded catch-up; the server additionally bounds steps per timer callback so stepping can't starve its HTTP serving). Two discoveries: the display world had been running on *simulation* time copied in every frame — it now has its own wall-clock `TimePlugin` (`addSystem` requires `TimeResource` to exist); and `Optional()` does not support absent resources (`getArg` throws), so optional resources are read via `GetWorld`.
3. ~~**Logical time.**~~ **Done by construction:** with the fixed timestep, `time.time` is tick-derived logical time, so its consumers (projectile lifespan via `CreateTime`, NPC retarget timers) are deterministic. `stat.ts` delta throttling still uses the wall clock deliberately — it is network-layer pacing, not simulation state.
4. ~~**Seeded RNG resource.**~~ **Done.** `Random` (sfc32) + `RandomResource` in nova_ecs, seeded per system from `fnv1a(systemId)` in `makeSystem`; state is get/settable for snapshots. Converted: weapon inaccuracy, submunition cones, beam inaccuracy, NPC target selection, ship spawn position provider. `make_ship.ts` keeps `Math.random` deliberately (creation-time state for player-spawned ships, synced as full state, never re-derived by the sim).
5. ~~**Deterministic entity IDs.**~~ **Done.** `IdFactory` resource (`kind:counter` ids) replaces `v4()` for projectiles, blasts, beams, and bay ships (bay ids are prefixed with the multiplayer owner since they sync across peers). The counter is simulation state: include it in rollback snapshots along with the RNG state.

**Milestone:** the determinism gate now passes *with NPC combat* — 8 NPCs fighting for 1200 steps produce bit-identical state hashes across two runs (`determinism_check.js 8 1200`), and a 4-NPC/240-step variant runs in CI. Caveat: both runs share warm game-data caches; item 6 still owns the cold-cache/cross-machine async-loading risk.
6. ~~**Synchronous data access in the sim.**~~ **Done — "stage, load, then insert."** Rather than preloading the full game files (too expensive), entities are staged: before insertion, `entity_data_loader.ts` loads the *transitive closure* of game data the entity and anything it can spawn will need synchronously (ship → outfits → weapons → submunition chains → hurtbox sprite sheets → bay fighter classes, recursively), and primes the lazily-built `WeaponEntries`. The insertion tick is an input, so it may vary; what never varies is data resolving mid-step. All sim `ProvideAsync`s became `ProvideFromCache` (synchronous, reading warmed `getCached`; may return undefined = retry next step), `makeSystem` loads planets before the world ever steps, and the bridge's `addEntity`/`spawnNpc` stage before inserting. Result: **worlds are deterministic from tick 0 with zero warmup** — the CI gates now assert this. Deferred to Phase 3: entities arriving via multiplayer state bypass staging and use the retry path (self-healing but with a varying attach tick); the input-exchange protocol should stage them too, buffering deltas for staged entities and applying them on insertion.
7. **Decision checkpoint: passed.** Same-machine replay is bit-identical from tick 0 (quiet and combat worlds); cross-browser trig is deferred per the Chrome-only decision. Phase 2 (snapshot/restore + local rollback) is unblocked.

### Phase 2: Snapshot, restore, and local rollback

0. ~~**Entity deriver registry.**~~ **Done.** Derived components (ship data, outfits, physics, weapons state, planet data) are now attached by *derivers* — `{provided, requires, derive}` entries that plugins register next to their systems (`entity_factory.ts`), run to a fixpoint by `completeEntity` at staged insertion. This keeps mod ergonomics (register a deriver, no central factory to edit) while making derivation synchronous and callable anywhere — which snapshot restore requires: a restored entity must be complete *before* resimulation begins, not one tick later. The `Provide`/`ProvideFromCache` systems remain as the fallback layer for un-staged arrivals; they get deleted when Phase 3 stages all ingress. Remaining sync-only providers (animation, hulls, shields, targets…) migrate to derivers as part of deciding the snapshot representation below (snapshot-and-restore them vs. re-derive on restore).
1. ~~**Full-world snapshot.**~~ **Done.** `snapshotWorld`/`restoreWorld` (nova_ecs `snapshot_plugin.ts`) with a per-component policy registry configured in nova (`snapshot_policies.ts`): **codec** (io-ts roundtrip, the default for registered components; the encoded form is structurally cloned because io-ts optimizes all-identity codecs to return the *live object* — the sneakiest bug of the effort), **share** (immutable static data like ShipData, and per-step-recomputed structures like hulls — the structural-sharing win), **clone** (mutable unregistered state: weapon reload timers, sub counts, collision sets), **skip** (multiplayer machinery; re-derived state like ShipPhysics, reattached synchronously via the deriver registry at restore). Resources: time, RNG state, id counter, control state. Entities restore in insertion order; restore discards the Add/Delete events its own surgery queues (`World.clearEventQueue`), since snapshots are taken between steps. The unhandled-component list is asserted empty in CI so new state can't silently bypass snapshots. Also fixed en route: projectile entity pooling (`FactoryQueue`) removed — the pool was unsnapshotted state (resim dequeued different objects, leaking `targetSpeed`/`BlastIgnore` across timelines); projectiles are built fresh per shot, and display-side sprite pooling already covers the perf motivation. **Acceptance (CI): restore is hash-exact, 180 steps of NPC combat resimulate bit-identically after restore, and repeated restores from one snapshot yield identical runs.** Measured on a 99-entity combat world: snapshot 0.76ms mean (snapshot-every-tick at 60 Hz is affordable), restore 4.2ms, step ~1.1ms — a 10-tick rollback ≈ one frame budget.
2. ~~**Ring buffer.**~~ 3. ~~**Rollback driver.**~~ 4. ~~**Local validation.**~~ **All done** — `RollbackSimulation` (nova_ecs `rollback_plugin.ts`): a snapshot ring buffer (default 64 ticks) plus a tick-keyed input history, with `setInputs(tick, inputs)` / `step()` / `rollbackTo(tick)`. The driver is prediction- and network-agnostic: whoever owns the network amends past inputs and requests the rollback. Both validation harnesses pass in CI with real control inputs steering the ship through combat: the *rollback fuzz test* (random inputs, random rollback depths → bit-identical to the straight-line run) and the *delayed-echo test* (inputs arrive 8 ticks late against a no-new-input prediction, corrected by rollback → converges exactly to the undelayed run). This is the netcode loop, minus the sockets.
5. ~~**Performance budget.**~~ **Measured** (99-entity combat world): snapshot 0.76 ms, restore 4.2 ms, step 1.1 ms — snapshot-every-tick at 60 Hz is affordable and a 10-tick rollback fits in roughly one frame.

**Phase 2 is complete.** ~~Flagged for Phase 3: platform-gated sim systems.~~ **Fixed**: `ShipController` and `WeaponPlugin` built different system sets per platform (an uncaught bug — clients controlled all NPCs, so the server never noticed). All simulation systems now build on every platform; only keyboard capture and key-mapping loading stay browser-side. A CI gate asserts a node world and a worker world simulate identically through combat with inputs. This also killed the recurring `window is not defined` worker rejection (`SetControlledShip` touched `window` unguarded). Node test harnesses use the `'worker'` platform (with a disk-backed `getSettings`) to match the real client sim. Parked: on player death, restore the player's entity state from a snapshot taken at launch/jump-in (per-entity restore is a natural extension of the snapshot machinery) instead of teleporting to the origin.

### Phase 3: Input-exchange network protocol

1. ~~**Tick-stamped input message.**~~ **Done (local).** `SimulationInput` (`simulation_input.ts`): control events, entity insertion/removal, jump route — structured-cloneable records applied at the start of their tick. The bridge host no longer mutates the world: it stages (loads an entity's data closure), then *schedules* an input, and `RollbackSimulation` records and applies it — the identical path resimulation replays. NPC spawns are staged host-side and become insertion inputs (which required registering the NPC AI components with the serializer, multiplayer-excluded, so they survive the encode roundtrip). Single-player now runs the netcode loop with one peer, and `window.novaSim.rewind(ticks)` live-rewinds the game — verified in the browser. Still missing for the wire: `peerId` scoping (jump route targets the local `PlayerShipSelector` for now) and land/depart as inputs. Note: incoming *multiplayer* messages still mutate state outside the input model; steps 2–3 replace that pipeline.
2. **Server as relay + clock + archive.** Reuse the existing socket/room layer. Per room, the server: assigns the canonical start tick, relays each peer's inputs to the others, retains the input log, and keeps a periodic snapshot for joins. It runs no simulation for rollback rooms.
3. **Prediction and delay.** Local inputs are applied at `tick + d` (small configurable input delay); remote inputs are predicted as repeat-last-input; receipt of authoritative remote inputs older than the current tick triggers rollback.
4. **Desync detection and recovery.** Peers attach their state hash for tick `t - N` to outgoing input messages; on mismatch, the affected peer requests a full snapshot resync — the existing multiplayer full-state machinery is repurposed as the recovery path rather than the steady-state path.
5. **NPC and world authority.** NPCs, projectiles, and all sim-derived entities are simulated identically by every peer and have no owner. `MultiplayerData` ownership shrinks to mapping peers to their input streams (which ship each peer controls). Within a rollback room, this *replaces* the delta-based sync of `multiplayer_plugin.ts`.
6. **Join and system transition.** A joining peer receives the latest server snapshot + the input log since that snapshot, simulates forward to the live tick, then participates normally. Hyperspace jumps are a leave/join across rooms.

### Phase 4: Hardening and polish

Only after 3 works end-to-end: input compression/batching, tuning input delay vs. rollback depth, spectators, and replay files (which fall out of the input log for free).

## Decisions

1. **Browser support:** all clients assumed to run latest Google Chrome. No deterministic math layer needed initially; periodic ship state broadcasts (position/velocity/rotation) are the drift backstop.
2. **Tick rate:** target 60 Hz; 30 Hz is the acceptable fallback if the Phase 2 benchmark demands it.
3. **Players per system:** ≤ 8–10 per room.
4. **Fallback:** server-authoritative with client-side prediction is acceptable only if it avoids input-round-trip floatiness — the local ship must be predicted locally, never "send keypress, wait for server to say what happened" (a local preview of the attempted action is fine). Phases 0–1 are prerequisite work for that design too, so nothing is wasted up to the Phase 2 checkpoint.

## Carried-over cleanup notes

- `SerializerResource` no longer cleanly means "things that go over multiplayer" — it also serves sim→display sync and will serve snapshots. Split the policy: one component include-list per consumer (display sync, snapshot/rollback, network join sync), likely with a shared registration core. `ExcludedMultiplayerComponentsResource` is the short-term version of this and should be absorbed into that split.
- Snapshot inclusion policy is a *third* include-list: it must cover strictly more than display sync (all sim-affecting components + resources) but can exclude anything derivable.
